
# FreeRTOS での機能比較の実施手順（検証項目1〜6）

MCP の概要と各ツールのセットアップは [mcp-basics.md](mcp-basics.md) および各ツールの手順書を参照。

## 検証用の共通準備

Windows ネイティブ環境を前提とします（コマンドは PowerShell 表記）。  
エージェントは Claude Code と GitHub Copilot Chat（VS Code、Agent モード）の**両方で実施**します。  
比較の単位は「1エージェント × 3ツール（Serena / codebase-memory-mcp / CodeGraph）× Q1〜Q6」で、これを2エージェント分行います。

```powershell
# 検証用ディレクトリにリポジトリを取得（タグ固定で再現性を確保）
git clone --revision=9b777ae5c5b8e9e456065a00294d1e5f5f9facf5 --depth 1 https://github.com/FreeRTOS/FreeRTOS-Kernel.git
cd FreeRTOS-Kernel
```

> 上記はV11.3.0時点でのSHAを指定している。最新安定版を確認して比較に利用すること。

## 比較の実施ルール

結果の再現性のため、以下を固定します。

1. **同一コミット・同一エージェント・同一モデル**で1セットを完結させる（エージェント種別（Claude Code / Copilot）・モデル・バージョンを記録）。  
ツール間比較はエージェント内で閉じ、エージェント間比較は同一ツールの結果同士で行う。
2. **クエリごとに新規セッション**で実施（前の回答がコンテキストに残ると後続クエリが有利になるため）
3. **比較対象の MCP は1つだけ有効化**（`.vscode/mcp.json` / `.mcp.json` を切り替える。複数有効だとエージェントが混ぜて使う）
4. **内蔵ツールへのフォールバックを禁止する**。素の Grep/Read で答えられてしまうと MCP の比較にならないため、全プロンプトに以下の前置きを付けます。

   > このリポジトリに関する質問です。回答には MCP ツール（serena / codebase-memory-mcp / codegraph）のみを使用し、内蔵の Grep・Glob・Read・Bash は使用しないでください。ツールで確認できなかった内容は「不明」と答えてください。推測で補完しないでください。

   ※ この禁止は **MCP ツール単体の性能を測るための実験統制**であり、実運用の推奨設定ではありません。実運用での使い分けは mcp-basics\.md の付録Aを参照。

5. **各クエリ3回実施**し、中央値を採用（LLM 側の揺らぎを均すため）
6. 記録項目: 正答性 / ツール呼び出し回数 / トークン消費（Claude Code の `/cost` または `/context` の差分。Copilot はトークンを直接確認する手段がないため空欄とし、呼出回数・所要時間で代替する）/ 所要時間 / フォールバック発生の有無

## 検証項目の詳細

各項目は「目的 → 投入プロンプト → 正解データの作成手順 → 採点基準」の順です。

**正解データはコミット `9b777ae5` 時点のものを [answers/](answers/)（q1\.md〜q6\.md）に作成済み。**  
対象コミットを変えた場合のみ、各項目の手順で再作成する。コマンドはすべて Windows PowerShell で、クローンしたリポジトリルート（`FreeRTOS-Kernel/`）で実行する前提。  
再作成時は先に保存先（本リポジトリの docs/answers）を変数に設定しておく。

```powershell
$ans = "<本リポジトリ>\docs\answers"   # 環境に合わせて実パスを設定
```

### 項目1: クロスファイル参照（ベースライン）

**目的**: 最も基本的な「この関数の呼び出し元は誰か」。grep でも解ける難度で、全ツールが満点を取れることを確認する足切り問題。

**プロンプト**:
> `vListInsertEnd` 関数を呼び出している関数をすべて列挙してください。呼び出し元の関数名とファイル名をセットで挙げてください。

**正解の作成**:

```powershell
Get-ChildItem -Recurse -Include *.c, *.h | Select-String -Pattern "vListInsertEnd"
```

出力から「定義（list.c）」「プロトタイプ宣言（list.h）」を除外し、呼び出し行だけを残す。各呼び出し行がどの関数の中にあるかをエディタで目視特定し、[answers/q1.md](answers/q1.md) に「呼び出し元関数名 / ファイル / 行番号」の表として保存。

**採点**: 正解集合に対する再現率（漏れ）と適合率（誤検出）を記録。定義や宣言を「呼び出し元」として混ぜたら誤検出扱い。

### 項目2: マクロ・エイリアスの解決

**目的**: FreeRTOS の公開 API はマクロ包装が多い（`xSemaphoreGive` は実体が `xQueueGenericSend` の呼び出しマクロ）。プリプロセス前を見る tree-sitter とプリプロセス後を見る clangd の差が最も出やすい項目。CC-RX 実案件コードへの外挿性が高い。

**プロンプト**:
> `xSemaphoreGive` の実体は最終的にどの関数ですか。マクロ展開を追って実体の関数名を特定し、さらにその実体関数の内部から呼び出される関数を3つ挙げてください。

**正解の作成**:

```powershell
Select-String -Path include/semphr.h -Pattern "define xSemaphoreGive"
# → 展開先の関数名を確認（queue.c 内の実装関数）
Select-String -Path queue.c -Pattern "xQueueGenericSend" | Select-Object -First 10
```

`include/semphr.h` の `#define` を目視で辿り、実体関数と、その関数本体から呼ばれる関数（`queue.c` を目視）を [answers/q2.md](answers/q2.md) に記録。

**採点**: (a) 実体関数名の特定 (b) 内部呼び出し関数の列挙、を分けて採点。(a) を外した時点で 0 点。

### 項目3: 条件コンパイルの理解

**目的**: config マクロによる可視性の判定。`--preprocess` を検討している `mtpj_deps.py` と同じ問題意識で、実務価値が高い。

**プロンプト A**:
> `vTaskDelete` 関数はどの設定マクロが定義されているときに存在しますか。該当する `#if` 条件を答えてください。

**プロンプト B**:
> `configUSE_TIMERS` を 0 にした場合、`timers.c` で定義される公開関数のうちコンパイル対象から外れるものを列挙してください。

**正解の作成**:

```powershell
Select-String -Path tasks.c, include/task.h -Pattern "INCLUDE_vTaskDelete"
Select-String -Path timers.c -Pattern "configUSE_TIMERS" | Select-Object -First 5   # ファイル全体を囲う #if を目視確認

# 関数定義の一覧づくりの補助（timers.c は #if 内のため本体が4スペースインデントされている。
# プロトタイプ宣言や static 関数も混ざるので目視で除外する）
Select-String -Path timers.c -Pattern "^    (static\s+)?[A-Za-z_]\w*(\s+\**\s*|\s*\*\s*)[A-Za-z_]\w*\("
```

timers.c 冒頭の `#if ( configUSE_TIMERS == 1 )` の範囲に含まれる関数定義を目視列挙し [answers/q3.md](answers/q3.md) へ。

**採点**: A は条件式の正誤（完全一致でなくても意味が合っていれば正解）。B は列挙の再現率・適合率。「Serena は compile_commands.json の構成でプリプロセス済みのため、無効側のコードが見えない/逆に確定的に答えられる」等、**各ツールの答え方の質の違いを備考欄に必ず記録**する。

### 項目4: 同名シンボルの多重定義（portable/）

**目的**: `pxPortInitialiseStack` は portable/ 以下の各ポートに多数定義がある。全候補を列挙して曖昧さを提示できるか、1つを勝手に選ぶかを見る。ここは正解が1つではなく、**挙動の違いを記録する項目**。

**プロンプト**:
> `pxPortInitialiseStack` 関数の定義はこのリポジトリのどこにありますか。複数ある場合はすべて挙げてください。

**正解の作成**:

```powershell
Get-ChildItem portable -Recurse -Filter *.c | Select-String -Pattern "pxPortInitialiseStack" -List |
    ForEach-Object { Resolve-Path -Relative $_.Path } | Sort-Object | Set-Content $ans/q4_files.txt
(Get-Content $ans/q4_files.txt | Measure-Object -Line).Lines   # 定義ファイル数を記録し answers/q4.md へ
```

**採点**: 列挙数 / 全定義数を記録。予想される挙動: codebase-memory-mcp と CodeGraph は全ポートを列挙（いずれも tree-sitter の網羅ビュー）、Serena は compile_commands.json に含まれるポート（MSVC-MingW）1件のみ。**いずれも「仕様通り」であり優劣ではない**ので、採点表では点数ではなく挙動として記録し、「単一構成の正確なビューと全網羅ビューのどちらが自分のユースケースに合うか」の判断材料にする。

### 項目5: 不透明ハンドル → 構造体の解決

**目的**: `TaskHandle_t` → `struct tskTaskControlBlock *` → `TCB_t` の typedef 連鎖を辿り、さらにメンバアクセスの read/write を区別できるか。型解決の質が最もはっきり出る。

**プロンプト**:
> `TaskHandle_t` の実体の構造体は何ですか。typedef の連鎖を示した上で、その構造体の `uxPriority` メンバに**代入（書き込み）**している箇所を tasks.c からすべて挙げてください。

**正解の作成**:

```powershell
Select-String -Path include/task.h, tasks.c -Pattern "tskTaskControlBlock" | Select-Object -First 10
Select-String -Path tasks.c -Pattern "uxPriority" | Set-Content $ans/q5_all.txt
```

`q5_all.txt` の各行を目視し「書き込み（`=` の左辺、`++` 等）」と「読み出し」に分類。書き込み行のみ [answers/q5.md](answers/q5.md) へ。

**採点**: (a) typedef 連鎖の正しさ (b) 書き込み箇所の再現率・適合率（読み出しを混ぜたら誤検出）。

### 項目6: 関数ポインタ経由の呼び出し（限界確認）

**目的**: タイマコールバックのような間接呼び出しは静的解析の限界域。3ツールとも完答できない可能性が高く、**「できないことをどう答えるか」の質**（不明と言えるか、幻覚を出すか）を比較する。

**プロンプト**:
> ソフトウェアタイマのコールバック関数はどこで登録され、どこで実行（呼び出し）されますか。登録箇所と実行箇所をファイル名・関数名で答えてください。

**正解の作成**:

```powershell
Select-String -Path timers.c, include/timers.h -Pattern "pxCallbackFunction"
```

登録箇所（`xTimerCreate` 系での格納）と実行箇所（`prvProcessExpiredTimer` 等での間接呼び出し）を目視特定し [answers/q6.md](answers/q6.md) へ。

**採点**: 登録・実行それぞれの特定可否に加え、**幻覚（存在しない関数名・行の捏造）が出たら大きく減点**。「グラフ/LSP では追えない」と正直に答えた場合は部分点。

## 判定の目安

- Q1 で満点を取れないツールはその時点で採用外。
- 実務（CC-RX プロジェクト）への外挿は **Q2・Q3 の結果を最重視**する（マクロ包装・条件コンパイルだらけのため）。
- ただし Serena の Q2・Q3 の好成績は「compile_commands.json がある前提」の成績である点に注意。**CS+/CC-RX 案件では compile_commands.json の生成自体が課題**なので、最終判断は「Q2・Q3 の性能差」×「自案件で clangd を成立させるコスト」の掛け算で行う。
